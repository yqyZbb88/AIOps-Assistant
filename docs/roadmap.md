# AIOps-Assistant 后续拓展计划书

版本基线：`0.3.0`  
文档状态：规划稿  
适用范围：单主机启动，逐步扩展到多主机和可观测运维平台

## 一、计划目标

后续拓展围绕四个目标推进：

1. **更容易部署**：让用户在本地或测试环境中可以一条命令拉起完整监控链路。
2. **更容易观察**：让告警、巡检、诊断、审批和 AI 建议有统一的人类可读入口。
3. **更可靠地使用 AI**：给模型调用和工具调用增加超时、熔断、降级和审计边界。
4. **更安全地扩展**：保持白名单、人工审批、只读诊断和配置化指标这些既有优势。

总体原则：

- 先完善单主机能力，再扩展多主机。
- 先保证安全和可验证，再增加自动化程度。
- Prometheus 继续负责阈值告警，AIOps-Assistant 不重复实现告警平台。
- 不提供任意 Shell、任意 PromQL 或不受控的写命令。
- 新增能力必须可配置、可审计、可降级、可测试。

## 二、当前项目基线

当前项目已经具备较完整的工程底座：

- FastAPI API 层和 Bearer Token 鉴权。
- Prometheus 指标查询和统一指标目录。
- Alertmanager Webhook 接收。
- 按 `alertname` 匹配的规则引擎。
- 规则写命令白名单。
- Agent 写命令人工审批。
- SSH 只读诊断命令白名单。
- 周期巡检和异常巡检归档。
- SQLite 会话、告警、处置、AI 建议和巡检归档。
- 工具结果数据时效说明。
- 离线测试体系，当前测试全部通过。

当前主要边界：

- 不支持多主机选择。
- 不支持多 worker 下可靠的审批和调度。
- 审批状态不跨进程重启恢复。
- 配置修改后需要重启。
- 没有内置一键监控栈。
- 没有面向普通用户的状态页面。
- 没有通用的 AI 调用熔断和预算控制。
- 没有受控的日志查询工具。
- 规则动作目前只按 Alertmanager 的 `alertname` 匹配。

## 三、参考项目的取舍

参考项目值得借鉴的部分：

- Docker Compose 一键拉起 Prometheus、Alertmanager、Node Exporter 和 Grafana。
- 告警到诊断结果的可视化展示。
- 用“感知、告警、思考、行动”解释系统闭环。
- 提供可操作的故障演示路径。
- 明确展示 Agent 工具、告警接收和诊断结果的连贯关系。

参考项目中不直接采用的部分：

- `shell=True` 执行模型传入的任意命令。
- 直接 `kill -9` 进程。
- 无鉴权的 Webhook 和 UI。
- 内存中保存诊断历史。
- 硬编码模型密钥和目标地址。
- 使用容器镜像的 `latest` 标签。
- 直接把 `grafana.db` 作为配置提交。
- 没有测试、审批、审计和幂等控制的写操作。

## 四、后续版本路线

### 版本 0.4.0：可部署、可观察、可验证

主题：把现有单主机能力变成更容易启动和使用的版本。

| 编号 | 项目 | 交付内容 | 验收标准 |
|---|---|---|---|
| P0-1 | 日志脱敏 | 对 API Key、密码、Token、SSH 参数和命令输出增加统一脱敏规则 | 日志、审计和告警归档中不出现明文敏感值 |
| P0-2 | 开发监控栈 | 增加 `deploy/dev/docker-compose.yml`，固定镜像版本，启动 Prometheus、Alertmanager、Node Exporter、Grafana | 新环境按文档执行后可完成一次完整告警链路 |
| P0-3 | 示例告警规则 | 使用当前 `metrics.yaml` 指标重写 CPU、内存、磁盘、Exporter Down 规则 | `promtool check rules` 通过，规则能实际触发 |
| P0-4 | 状态页面 | 增加只读状态页面，展示健康状态、活动告警、最近巡检、待审批和最近 AI 建议 | 页面只读，支持鉴权，不产生写操作 |
| P0-5 | 健康检查增强 | 保留 `/health` 兼容行为，增加依赖组件和准备状态 | 能区分进程存活、存储降级、Prometheus 不可达等情况 |
| P0-6 | 部署文档 | 增加一分钟启动、五分钟演示和故障排查文档 | 新用户不依赖开发人员即可完成演示 |

建议优先完成的顺序：

```text
日志脱敏
→ 开发监控栈
→ 状态页面
→ 健康检查增强
→ 示例告警和 Dashboard
```

### 版本 0.5.0：AI 可靠性和人工协作

主题：让 AI 在失败、超时、重复调用和人工审批场景下更可控。

| 编号 | 项目 | 交付内容 | 验收标准 |
|---|---|---|---|
| P1-1 | LLM 熔断 | 增加超时、连续失败熔断、冷却恢复和调用指标 | LLM 不可用时聊天和告警接收不被长时间阻塞 |
| P1-2 | 调用预算 | 增加单轮调用次数、token 和工具数量上限 | 异常循环不会无限调用模型或工具 |
| P1-3 | 审批恢复 | 持久化待审批项，明确区分已执行、未执行和结果未知 | 进程重启后不会执行陈旧命令，也不会静默丢失状态 |
| P1-4 | 受控日志查询 | 新增只读日志查询源，限制文件、路径、行数和字符数 | 不提供任意文件读取，不泄露密钥 |
| P1-5 | 通知渠道 | 将当前终端输出抽象为通知接口，支持 Webhook、钉钉或企业微信 | 告警和处置结果可推送到外部渠道 |
| P1-6 | AI 运行审计 | 记录模型、提示词版本、工具名称、耗时和结果摘要 | 可以追踪一次建议由哪些工具和模型产生 |

### 版本 0.6.0：配置化和扩展性

主题：减少重启，支持更多主机和更多诊断来源。

| 编号 | 项目 | 交付内容 | 验收标准 |
|---|---|---|---|
| P2-1 | 安全热更新 | 支持 `metrics.yaml`、`rules.yaml`、`diagnostics.yaml` 的校验后原子替换 | 配置错误时保留旧配置，不使服务进入半失效状态 |
| P2-2 | 规则动作扩展 | 保持 Alertmanager 为告警源，扩展动作参数模板和动作类型 | 不绕过 `actions.yaml` 白名单和审批策略 |
| P2-3 | 主机注册表 | 增加 `hosts.yaml` 或等价模型，描述实例、SSH 目标和标签 | 指标、诊断和动作能按主机选择器定位 |
| P2-4 | 多主机巡检 | 巡检支持主机选择、每主机结果和汇总等级 | 单主机失败不影响其他主机巡检 |
| P2-5 | 本机诊断适配器 | 可按配置启用本地只读诊断，但必须走 `DiagnosticSource` 白名单 | 不允许模型传入任意命令 |
| P2-6 | 轻量监控面板 | 提供 Grafana Dashboard JSON，不使用 `grafana.db` | Dashboard 可通过 JSON 导入并适配当前指标 |

### 版本 1.0.0：生产化与多 worker

主题：从单进程工具升级为可长期运行的生产服务。

| 编号 | 项目 | 交付内容 | 验收标准 |
|---|---|---|---|
| P3-1 | 多 worker 审批 | 使用共享数据库或租约实现审批、幂等和任务抢占 | 任意 worker 都能得到一致的审批结果 |
| P3-2 | 外部调度 | 支持独立 scheduler 或外部 cron，避免多 worker 重复巡检 | 同一周期只执行一次 |
| P3-3 | 容器化和守护进程 | 提供 Dockerfile、Compose 或 systemd 部署模板 | 支持健康检查、信号退出和日志挂载 |
| P3-4 | 备份与恢复 | 明确数据库迁移、备份、恢复和保留策略 | 模拟损坏数据库后可恢复 |
| P3-5 | 安全加固 | TLS、反向代理、密钥管理、文件权限和依赖扫描 | 生产部署检查表全部通过 |
| P3-6 | 自身可观测性 | 增加 AIOps-Assistant 自身的指标、追踪和告警 | 能观察队列、失败率、延迟和存储状态 |

## 六、建议新增的架构接口

后续扩展继续沿用当前分层，不把逻辑塞进 API 或 Agent：

```text
API / UI
   ↓
Core Service
   ↓
Interfaces
   ├── MonitorSource
   ├── DiagnosticSource
   ├── AgentActionSource
   ├── HistoryStore
   ├── InspectionStore
   ├── SessionStore
   └── Notifier
```

建议新增：

- `LogQuerySource`：只读日志查询接口。
- `Notifier`：告警、处置、审批和巡检通知接口。
- `LlmResilience`：超时、熔断、重试和预算控制。
- `HostRegistry`：多主机元数据和选择器。
- `SchedulerLease`：多 worker 下的调度租约。

## 七、验收和测试要求

每个阶段都必须满足：

- 离线测试不访问真实 Prometheus、LLM、SSH 或公共网络。
- 新增数据库结构必须包含迁移和版本测试。
- 新增写能力必须有白名单、参数校验、审批和审计。
- 新增读能力必须有长度、路径和权限限制。
- 新增配置必须有严格校验和示例。
- 用户文档不得依赖开发者内部说明。
- 变更后必须保留旧接口兼容性，除非明确发布破坏性变更。

## 八、暂不做事项

以下内容不进入当前路线：

- 让模型执行任意 Shell。
- 让用户提交任意 PromQL。
- 无审批执行危险写命令。
- 直接终止任意进程。
- 把大模型当作唯一告警源。
- 在没有验证和回滚能力时宣称“完全无人值守”。
- 把数据库文件、日志和密钥提交到 Git。

建议第一个迭代只做以下五件事：

1. 完成日志脱敏。
2. 增加开发用 Docker Compose 监控栈。
3. 增加只读状态页面。
4. 增强健康检查和依赖状态展示。

完成这五项后，项目会从“工程能力完整的单主机助手”升级为“可快速部署、可观察、可验证的单主机 AIOps 平台”。
