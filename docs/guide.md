# 日常使用指南

这篇说明从“项目已经启动、可以打开控制台”开始。
还没有启动项目时，先看 [快速入门](quickstart.md)。页面按钮的更多说明见 [控制台说明](console.md)。

## 从搭建到使用，按这个顺序

不必一次打开所有功能。先看得到数据，再尝试 AI、SSH 和执行命令。

| 顺序 | 要做的事 | 完成后应该看到什么 |
|---|---|---|
| 1 | 启动项目，用 Token 连接 | local-node 有数据 |
| 2 | 在真实服务器安装 Exporter，再添加到控制台 | 能看到这台服务器的指标 |
| 3 | 配置 AI 模型 | 能结合指标回答问题 |
| 4 | 准备 known_hosts 和 SSH 登录信息 | SSH 连接测试通过 |
| 5 | 开启并授权只读诊断 | 能读取内存、磁盘明细 |
| 6 | 创建普通用户，选择他能看的主机 | 用户只看到获准访问的主机 |
| 7 | 在测试机练习审批和日志标记 | 拒绝不执行，批准后有标记和记录 |
| 8 | 在单独的测试环境练习告警、重启和备份恢复 | 告警能收到，恢复后数据仍可查看 |

下面用几个固定的示例名字，方便对照操作：

| 示例 | 是什么 |
|---|---|
| linux-test | 你在控制台给测试服务器起的主机 ID |
| linux-test-ssh | 保存这台服务器登录信息的凭据 ID |
| alice | 使用 Assistant 的普通用户 |
| ops | Linux 服务器上的登录账号，必须换成实际已有的账号 |

这些名字不需要相同。Assistant 用户和 Linux 登录账号是两回事。

## 先选主机，再看数据

在顶部选择要查看的主机，然后打开“总览”或“主机”页。
先看数据更新时间，再看 CPU、内存、磁盘和告警。没有数据不能按 0 理解。

想看变化过程，在主机页选择“区间指标”和时间范围，鼠标移到曲线上查看具体时间和值。
可以收藏常看的指标，之后从总览查看。详细按钮见 [指标和趋势](console.md#指标收藏和时间趋势)。

## 问答与只读诊断

1. 顶部选主机。
2. 进入“问答诊断”，新建会话，或打开这台主机的旧会话。
3. 输入问题，点“发送”，等回答完成。

没配置 AI 时，先问“CPU 使用率是多少”“内存使用率是多少”等简单问题。
配置 AI 后，再问“请结合当前 CPU、内存和告警分析是否存在异常”。
问题“状态”目前返回模拟文字，不能当作健康检查。

一条会话始终属于创建时选择的主机。切换顶部主机不会改变旧会话的目标；
排查另一台服务器时，要为它另建或选择自己的会话。
改名和删除在会话右上角“•••”菜单中。删除会话不能撤销已执行的远程操作。

“只读诊断”是让系统登录服务器，执行预先允许的查询，例如 free 和 df。
开启方法见 [第一次执行只读诊断](#第一次执行只读诊断)。

## 告警、巡检和记录怎么对应

| 页面里的记录 | 用来了解什么 |
|---|---|
| 活动告警 | Prometheus 目前认为哪些地方有问题 |
| 最近告警 | 本次启动后，Assistant 最近收到了哪些通知 |
| 告警历史 | 以前收到的告警及处理结果 |
| 异常巡检 | 系统定时检查时发现的问题 |
| 执行记录 | 执行了什么动作、对哪台主机执行、结果如何 |

查看时先选对主机，再看记录类型、时间和状态。历史里有告警，不代表现在还没恢复。
正常巡检主要写日志，不会每轮都产生异常记录。
pending 表示还在等待告警持续时间，firing 表示告警已触发，resolved 表示已恢复。

想自己触发告警，使用 [测试流程](testing.md#6-告警和异常恢复)。
模拟告警只用来检查通知能不能送到，不表示真实 CPU 或内存升高。

## 人工审批与执行

聊天中请求写操作后，系统会先生成申请。到“审批”页核对申请人、主机、动作和参数，
确定需要执行再批准，否则拒绝。同一申请只能处理一次。

管理员和审批人是不同角色。看不到申请时，检查当前用户是否有审批角色和目标主机访问权。
服务重启后，旧的未决申请不能继续批准。

执行结果是 unknown 时，意思是“结果还不能确认”，可能已经执行过。
先查执行记录和目标服务器，不要立刻重复申请。完整练习见 [第一次复现人工审批](#第一次复现人工审批)。

还有一种“规则自动处置”：它收到指定告警后直接执行允许的动作，不经过聊天审批。
这项功能单独配置，新手先在测试机用日志标记练习，见 [自动处置](#第一次配置告警规则自动处置)。

## 登记实际主机

要监控真实 Linux 服务器，先在那台服务器安装 Node Exporter，它负责采集指标。
安装和网络检查见 [安装 Exporter](deployment.md#独立-linux-测试主机安装-exporter)。
控制台“添加主机”只登记地址，不会替你在远端安装软件。

### 第一次通过向导登记 Linux 主机

**准备：** Exporter 已启动，项目能访问它的 9100 端口。
下面的 192.0.2.20 是示例地址，换成自己的测试服务器地址。

1. 管理员进入“系统管理 → 监控主机”，先保存或放弃其它未保存的修改。
2. 点“刷新目标”。已经在列表里的服务器直接选择；默认自管模式也能选择新增 Exporter。
3. 按下表填写，点“预览”，检查信息。
4. 第一次只看监控，可以不选 SSH，也不勾选诊断。
5. 点“新增并生效”。等几次采集后，顶部选 linux-test，打开“主机”页。

| 表单字段 | 填写示例 |
|---|---|
| 主机 ID | linux-test；小写字母开头，只用字母、数字和连字符，最多 63 位 |
| 显示名 | Linux 测试机 |
| 新 Exporter 主机:端口 | 192.0.2.20:9100，不加 http:// 或 /metrics |
| 已有 SSH 凭据 ID | 第一次可选“不配置 SSH” |
| SSH 端口 | 22；不是 Exporter 的 9100 |
| 只读诊断授权 | 第一次留空 |

**看到什么算成功：** 主机列表出现 linux-test，指标有值，观测时间继续更新。
只有“添加成功”但没有数据时，去 Prometheus 的 `/targets` 检查该目标是否为 up。
默认新增目标的 job 是 aiops-hosts，instance 是填写的地址:端口；它们是 Prometheus 用来区分目标的标签。
检查时必须与实际目标一致。详细排查见 [监控无数据](troubleshooting.md#prometheus-与-exporter只读分层检查)。

<details>
<summary>已有外部 Prometheus，或者想在新增时一起配置 SSH？</summary>

页面显示“外部 Prometheus”时，只能选择外部已采集的目标，先由维护者添加采集配置。
新增时要授予诊断，先准备 SSH 凭据、启用只读诊断目录，再选凭据并点“测试 SSH”。
测试通过后才勾选诊断并保存；编辑太久需要重新测试。
SSH 不是 22 端口时，最好在本次新增时一起填写正确端口。

</details>

### 准备并关联 SSH 凭据

**准备：** 一套真实 Linux 登录账号和密码，或该账号的登录私钥。
另外按 [known_hosts 教程](deployment.md#获取并核验-ssh-known_hosts) 准备服务器公钥记录。

1. 打开“系统管理 → SSH 凭据”。
2. 凭据 ID 填 linux-test-ssh，用户名填目标 Linux 的实际登录账号。
3. 选择密码或私钥认证，填写密码或上传用户私钥；不能上传 .pub 公钥，也不支持带口令私钥。
4. 粘贴已核验的 known_hosts 原文，点“保存 SSH 凭据”。
5. 在下方找到 linux-test，选择 linux-test-ssh，点“更新关联”。
6. 点“测试已保存的 SSH 连接”。

**看到什么算成功：** 页面提示 SSH 主机密钥和认证通过。这还没有执行任何查询命令。
失败时看 [SSH 排查](troubleshooting.md#ssh-连接与-known_hosts-错误)。

已有主机原来没有 SSH 时，关联按钮默认使用 22 端口；原来已有 SSH 时保留其端口。
非 22 端口请在新增向导里填写，或由管理员修改运行 hosts.yaml 的 ssh.port 后应用配置。
更新共享凭据会影响所有使用它的主机；更新时留空敏感字段表示保留原值。

## 第一次执行只读诊断

**准备：** [模型已配置](console.md#第一次配置模型并验证问答)、聊天 Agent 已打开、
linux-test 的 SSH 连接测试通过。

1. 打开“系统管理 → 安全与开关”，开启“只读诊断目录”。
2. 到“命令目录 → 诊断命令”，确认 memory、disk 两项已启用。
   它们分别查询内存和磁盘，不需要使用 root。
3. 到“主机授权”，只为 linux-test 勾选 memory、disk。
4. 点顶部“保存并生效”。
5. 顶部选 linux-test，创建会话，逐条发送：

```text
请调用已授权的 memory 诊断，读取当前主机的内存明细并解释结果。
请调用已授权的 disk 诊断，读取当前主机的文件系统占用并解释结果。
```

**看到什么算成功：** 回答包含这台主机实际查询到的内存或文件系统明细。
只给建议、只复述监控指标，不能证明 SSH 诊断已执行。
如果没有调用工具，检查聊天 Agent、模型工具调用支持、命令开关和主机授权。

## 第一次复现人工审批

这次练习只向测试主机的系统日志写一条标记，不重启业务，也不清理磁盘。
先完成上面的模型和 SSH 设置。只在单独的测试环境练习。

### 先准备一个测试动作

在测试主机运行 `command -v logger`，确认有 logger。
确认 SSH 用户能写系统日志，验收人员能读取日志。

打开“系统管理 → 命令目录 → Agent 动作”，点“新增命令”，按下表填写：

| 字段 | 填什么 |
|---|---|
| 命令键 | test_marker |
| 启用命令 | 勾选 |
| 说明 | 写入测试主机验收日志标记 |
| 命令模板 | `logger -t aiops-acceptance -- {message}` |
| 使用 sudo | 不勾选 |
| 新增参数：参数名 | message |
| 参数类型 | str，表示文字 |
| 全匹配正则 | `^[A-Za-z0-9_-]{1,64}$`，限制为英文、数字、下划线、连字符，最多 64 个字符 |
| 默认值 | 留空 |
| 参数说明 | 本次验收的日志标记 |

接着在“安全与开关”打开“Agent 写动作目录”，审批模式选“指定审批人”，
确认当前验收用户有审批角色。在“主机授权”只给 linux-test 勾选 Agent 动作 test_marker，
然后点“保存并生效”。规则自动处置保持关闭。

### 先拒绝，再批准

1. 在 linux-test 会话请求：“请使用 test_marker 写入标记 acceptance_reject_01”。
2. 出现待审批申请后，先不要批准，检查目标日志里还没有这个标记。
3. 进入“审批”，核对主机、动作和参数，选择拒绝。目标日志仍不应出现该标记。
4. 再申请 acceptance_approve_01，核对后批准。
5. 查看会话和“运维记录”，并在目标主机查日志：

```bash
sudo journalctl -t aiops-acceptance --since '10 minutes ago' --no-pager
```

**看到什么算成功：** 拒绝的标记没有写入；批准的标记出现，并有对应执行记录。
没有 journalctl 的系统，用该系统实际的日志查看方式。日志权限不足不能算作“没有执行”。

结束时先处理所有待审批申请，再撤回 test_marker 的主机授权、关闭 Agent 写目录并保存。
没有引用后再删除测试命令。结果为 unknown 时先核对日志和记录，不要重复批准或重做动作。
更多情况见 [审批测试](testing.md#7-aissh-与人工审批按需执行)。

## 第一次配置告警规则自动处置

这条路径收到告警后可以直接执行，不经过人工审批。仍只用上面的日志标记练习。

1. 在“命令目录 → 规则动作”单独新增 test_marker，模板和参数沿用上一节。
   Agent 动作里的同名命令不会自动出现在这里。
2. 开启“规则动作目录”，为 linux-test 勾选规则动作 test_marker。
3. 新增告警规则：告警名 AIOpsAcceptance，主机 linux-test，动作 test_marker，
   message 填 rule_acceptance_01。先关闭该规则的自动执行和自动处置总开关，保存。
4. 按 [发送测试告警](testing.md#发送绑定测试主机的单条告警) 发送一次。
   应收到告警并留下匹配记录，但目标日志没有新增标记。
5. 确认只影响测试主机后，打开该规则的自动执行和总开关，保存，再发送一条新的测试告警。
6. 这次应出现执行记录和目标日志标记。结束后关掉测试规则和总开关，撤回授权并保存。

规则匹配不等于动作成功，要看执行结果和目标日志。命中规则但关闭自动执行时，
也不会转给 AI 分析。详细字段见 [规则配置](configuration.md#rulesyaml)。

## 修改配置与日常维护

在“系统管理”修改普通配置后，点顶部“保存并生效”。
SSH、Token、模型和新增主机使用各自分区的保存按钮。
提示冲突时，先处理正在运行的请求或待审批申请，再重新加载配置，不强行覆盖。

如果直接编辑服务器上的 YAML，改的是 `.runtime/config/`，然后在管理页点“应用磁盘配置”。
修改首次部署样例不会改变现有运行配置。哪些修改要重启见 [配置生效说明](configuration.md#字段生效与重启)。

| 日常任务 | 完整步骤 |
|---|---|
| 创建普通用户、选择能看的主机 | [用户与主机权限](auth.md#第一次创建普通用户并验证隔离) |
| 停止、启动、升级 | [部署与升级](deployment.md) |
| 触发告警、压测和恢复练习 | [测试流程](testing.md) |
| 备份和恢复数据 | [数据库备份](database.md#备份)、[整套部署备份](deployment.md#停机整栈备份) |
| 连接失败、无数据、保存失败 | [问题排查](troubleshooting.md) |
