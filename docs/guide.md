# 日常使用指南

本页组织已经启动的项目如何使用。首次运行见 [快速入门](quickstart.md)，部署、升级和
重建见 [部署与升级](deployment.md)，具体页面按钮见 [控制台说明](console.md)。

## 先选主机，再看数据

在控制台顶部选择当前主机。`host_id` 是监控、聊天、诊断与执行记录共同使用的定位键；
一条会话创建后不能改绑其它主机。为另一台主机排查时，选择那台主机自己的会话。

从“总览”和“主机监控”检查 Exporter 状态、CPU/内存/磁盘、观测时间与活动告警。
没有采样不等于使用率为 0，Exporter 不可达也不等于服务器已关机。趋势页按真实时间与设备分线，
即时与趋势查询状态独立显示。细节见 [指标与时间趋势](console.md#指标收藏和时间趋势)。

## 问答与只读诊断

在“问答诊断”新建或选中当前主机的会话，然后发送问题。
模型不可用时，指标和告警关键词仍可走兜底；复杂自然语言分析需要配置模型。
回答中的当前指标、历史巡检和建议要结合各自时间理解，历史异常不是实时健康结论。

SSH 诊断还要求管理员启用目录、配置已登记主机的 SSH 凭据，并授予该主机的
`allow.diagnostics`。问题文本不会变成自由 Shell，也不能让模型选择任意 SSH 地址。
完整能力配置见 [配置指南](configuration.md#八diagnosticsyaml)；页面行为见
[问答与诊断](console.md#问答与诊断)。

没有工具调用时，核对模型/Agent 开关、指标的 `chat` 范围、所选主机和命令授权。
请求失败或超时不代表服务端已经取消处理，重试前先看会话和执行记录。

## 告警、巡检和记录怎么对应

| 数据 | 能回答什么 | 不能据此推断什么 |
|---|---|---|
| 活动告警 | Prometheus 当前 pending/firing 告警 | Assistant 一定已经收到 webhook |
| 最近告警 | 当前 Assistant 进程最近收到的通知 | 重启前的完整历史 |
| 告警归档 | 收到的告警、规则处置与 AI 建议 | 目标目前仍然异常 |
| 异常巡检 | 按周期检查发现的异常轮次 | 没有记录就代表当前健康 |
| 执行记录 | 规则/Agent 动作状态、主机、动作和时间 | unknown 代表没有执行 |

正常巡检写日志，不进入异常归档。合成告警用于验证告警投递，不能用来证明真实 CPU
升高或巡检已经发现异常。读 API 时对应的数据来源与边界见
[告警、巡检和执行历史](api.md#告警巡检和执行历史)。

规则按告警名匹配并要求明确主机、命令与授权；无规则的告警才进入 AI 分析路径。
告警已收到但没有动作时，先按 [告警排障](troubleshooting.md#告警收到但没有动作) 核对，
不要直接开启自动处置。

## 人工审批与执行

Agent 写命令先产生待审批项，人工批准后才执行。批准前核对申请人、主机、动作、参数、
业务窗口及影响；不需要的申请应拒绝。管理员与审批人是独立角色，管理权限不自动赋予审批权。

同一 ID 只能消费一次。重启后旧申请不能继续执行，链式审批的下一轮保存失败时也不能
重放原 ID。执行状态为 `unknown` 时先对照执行/审计记录和目标状态，不要盲目再次批准。
具体状态与接口见 [会话、聊天和审批](api.md#会话聊天和审批)，授权范围见
[鉴权说明](auth.md#2-配置审批模式)。

规则自动处置是另一条路径，不经过 Agent 审批；应分别检查规则总开关、单规则自动执行、
命令启用、主机授权和幂等记录。

## 登记实际主机

首次 Compose 的 `local-node` 只观察栈内 Docker Linux 环境。
监控实际 Linux 服务器时，先由有权限的维护者在目标部署 Exporter，并确认 Prometheus
能够访问其端口，然后使用控制台主机管理入口新增目标。

外部 Prometheus 模式只能从已发现的目标选择；managed 模式可以登记文件发现目标。
登记不会安装或启动远程服务，SSH 检查只验证握手和认证，不验证 Exporter。
新主机默认不授予诊断或写权限；按需要选择已有凭据并逐项授权。

页面操作见 [新增主机](console.md#系统管理配置草稿与独立凭据保存)，目标与字段见
[主机配置](configuration.md#三hostsyaml)。现有记录可能引用主机，不要直接删除登记项。

## 修改配置与日常维护

管理员在“系统管理”中维护一份完整草稿，核对各分区后统一保存。
如果提示 revision 冲突，重新加载并人工合并；有执行中的操作、未决审批或审批状态无法
核对时也会拒绝热切换。不要绕过冲突强制覆盖。

页面外手改 YAML 后须显式应用磁盘配置。是否可以热应用由字段决定，部署环境密钥、Compose 发布端口、
SQLite/日志路径等需要重启；具体归类见 [字段生效与重启](configuration.md#十一字段生效与重启)。
手动修改应操作实际 `.runtime/config/`，不要改首次部署模板。

日常维护优先查看主机状态、异常趋势、告警是否投递、待审批和执行记录。
再按保留需求检查数据库大小、日志轮转与备份，轮换凭据前验证新的身份仍可登录。
